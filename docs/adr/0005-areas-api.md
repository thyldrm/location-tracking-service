# ADR 0005 — Areas API: validation, idempotent creation, outbox events and pagination

- **Status:** Accepted
- **Date:** 2026-10-08

## Context

Areas are created rarely, by operators or internal tools, but every area changes how millions of pings are
evaluated. A broken polygon would silently produce wrong entries, a duplicate area would produce duplicate entries,
and an area that exists in the database but never reaches the workers would produce no entries at all. Creation
requests travel over unreliable networks, so clients retry.

## Decisions

### Two-stage geometry validation

1. A Zod schema checks the GeoJSON document: `Polygon` only, closed rings of at least 4 positions, coordinate ranges,
   at most `AREA_MAX_VERTICES` positions. It is cheap, runs without I/O and reports precise field paths.
2. PostGIS checks the geometry (`ST_IsValid`), and its `ST_IsValidReason` text, which includes the location of the
   problem, is returned to the client. Re-implementing OGC validity rules in TypeScript was rejected: it is subtle
   (self-intersections, hole placement, touching rings) and PostGIS is already the source of truth. The
   `chk_areas_geometry_valid` constraint stays as the last line of defence.

Ring orientation is normalised to RFC 7946 (exterior counterclockwise, holes clockwise) in a pure function, so
stored and published geometries follow one convention whatever the client sent.

### Uniqueness through the index

Case-insensitive name uniqueness is enforced by `uq_areas_name_lower`. The violation is recognised by constraint name
and returned as `409`. A "does this name exist?" query before inserting was rejected: two concurrent requests can both
pass it (check-then-act race), and it costs an extra round trip on every request.

### `Idempotency-Key` claimed inside the creating transaction

Within one transaction: claim `(scope, key)` with `INSERT … ON CONFLICT DO NOTHING RETURNING`, insert the area,
append the outbox event. Consequences of this ordering:

- The key commits only together with the area: a failed request leaves no key behind and can be retried.
- A concurrent request with the same key blocks on the key's primary key until the first transaction ends, then
  replays its result. It never reaches the name check, so it never gets a misleading `409`.
- The resource id is generated by the application (UUIDv7) before the transaction, so the key row can store it
  before the area row is written.

A replay returns the original status and body with `Idempotent-Replayed: true`. Alternatives considered: storing the
full HTTP response (unnecessary, the area itself is immutable) and a Redis-based lock (a second system that can
disagree with the database).

### `area.created` through the outbox, carrying the full area

The event is written by `OutboxWriter` with the transaction's `EntityManager` and later published by the relay
(milestone 6). The payload carries the geometry (event-carried state transfer) so that workers update their in-memory
index without querying the database; at the vertex limit this is well under Kafka's default 1 MB message size.

### Keyset pagination

`GET /areas` orders by `(created_at DESC, id DESC)` and continues after the last row with the row comparison
`(created_at, id) < ($1, $2)`, which PostgreSQL evaluates as an index condition on `idx_areas_created_at_id`.
`created_at` is set by the application clock with millisecond precision so that the cursor round-trips exactly.

## Consequences

- Creating an area costs two round trips to PostgreSQL (validity check, then the transaction); acceptable for a rare
  operation and it keeps validation errors precise.
- Idempotency keys must be deleted after 24 h; this is part of the worker's housekeeping (milestone 6).
- `GET /areas` returns geometries in full. With the vertex limit and page size limit a page stays bounded, but a
  summary representation would be needed if areas became very large.
