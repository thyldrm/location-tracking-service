# ADR 0004 — Error responses, request correlation and structured logging

- **Status:** Accepted
- **Date:** 2026-10-08

## Context

A request crosses several processes: the API accepts a ping, the worker processes it minutes later if the
database was down, and the resulting event is consumed by other services. When something goes wrong, operators need
to find every log line that belongs to one request, and clients need errors they can handle programmatically
without seeing internals.

## Decisions

### Errors: RFC 9457 Problem Details from one global filter

- Every error response is `application/problem+json` with `type`, `title`, `status`, `detail`, `instance` and
  `correlationId`; validation errors add `errors`.
- Application code throws subclasses of `AppError` (`NotFoundError`, `ConflictError`, ...) that know their status and
  problem type. It never builds HTTP responses for errors itself.
- A single `ProblemDetailsFilter` converts anything thrown (application errors, NestJS HTTP exceptions, Fastify
  client errors, PostgreSQL errors, network errors, bugs) through the pure function `resolveProblem`. Transient
  database and network failures become retryable `503` responses with `Retry-After`; anything unexpected becomes an
  opaque `500` whose details go to the logs only.

Alternative considered: NestJS's default `{ statusCode, message, error }` body. Rejected because it is not a standard,
has no stable machine-readable error type and leaks framework messages for some errors.

### Correlation: AsyncLocalStorage instead of request-scoped providers

- The correlation id is resolved once per request (valid incoming `x-request-id` or a new UUIDv7), returned in the
  response header and stored in an `AsyncLocalStorage` context via `nestjs-cls`. `RequestContext` exposes it to
  application code and opens equivalent contexts for non-HTTP work (Kafka messages).
- Fastify's own request id is generated by the same function, so the framework, the HTTP logger and the context
  always agree on one value regardless of middleware order.
- Request-scoped NestJS providers were rejected: they force the whole dependency chain to be re-instantiated on every
  request, which is not acceptable at the target ingestion rate.

### Logging: pino, JSON to stdout

- `nestjs-pino` / `pino-http` write one JSON object per line to stdout; the platform ships logs (12-factor). The
  service never writes log files.
- Each request gets a child logger bound to `correlationId`, so application logs and the access log share it.
- Access logs use `warn` for 4xx and `error` for 5xx; health and metrics probes are not logged.
- Secrets are excluded by construction (headers are not serialized) and redacted as a second line of defence.
- `LOG_FORMAT=pretty` exists for local development only.

### Authentication: service API key

- A global guard requires `x-api-key` on every route unless marked `@Public()` (fail closed).
- Several keys can be active at once for rotation; comparison is constant-time on SHA-256 digests.
- End-user authentication remains the API gateway's job (SPEC §3).

## Consequences

- Adding a new error case means adding or reusing an `AppError` subclass; the HTTP mapping is automatic and tested.
- Any code, including future Kafka consumers, can read the current correlation id without threading it through
  function parameters.
- Unknown routes answer `404` before authentication runs (NestJS routing happens before guards).
